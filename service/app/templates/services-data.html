Services over a modern database

Move the business rules out of stored procedures and into services that the team can test and deploy. The data then moves to a modern database in steps, with each step checked before the next.

When it fits

Cutover recommends this when the findings show stored procedures, functions or views that hold logic, and code that reads and writes many tables.

Stored proceduresViews and functionsTables used in code

How the move goes

  1. List the routines. Use the routines and tables from the expanded findings to see what each piece of logic reads and writes.
  2. Write the services for one area at a time, with tests that compare their results with the old routines.
  3. Run both side by side and compare the outputs for real data before any switch.
  4. Switch each area over and retire the routines it replaced.
  5. Move the data to the new database last, in copies that are checked against the source.

What stays and what changes

Stays for now
  • The screens and how users work
  • The data itself, until the last step
Changes
  • Logic moves from the database into tested code
  • Schema changes are kept in migrations
  • The database engine can be replaced

Main risks

  • Routines often hold rules nobody wrote down. Compare outputs on real data before retiring any routine.
  • Reports and batch jobs may call routines directly. List them before the switch.
  • Date, rounding and text rules differ between engines. Test them explicitly.

This is a template, not a plan for one application. The routines and tables named in the review are the starting list.
