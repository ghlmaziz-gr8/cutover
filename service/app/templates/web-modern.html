Modern web front end over an API

Rebuild the screens as a modern web front end. A clean API sits in front of the data that already exists, so users get a current interface and the database stays as it is for now.

When it fits

Cutover recommends this when the findings show legacy page code, such as Classic ASP, JSP or ASP.NET Web Forms, with screens and endpoints the users reach directly.

Legacy pagesScreens foundEndpoints exposed

How the move goes

  1. Map the screens. Use the screen names and the page flow from the review to list every screen, and agree which ones matter most.
  2. Stand up the API. Put the business rules that live in the pages behind endpoints that return data, not HTML.
  3. Build the new front end one screen group at a time, starting with the simplest group, and run it beside the old pages.
  4. Move users across group by group, and retire each old page once its replacement has been used in production.

What stays and what changes

Stays for now
  • The database and its data
  • Existing login and roles
  • Stored procedures, until the services take them over
Changes
  • Every page is rebuilt as a screen in the new front end
  • Logic moves from pages into the API
  • Deployment moves to a modern pipeline

Main risks

  • Logic hidden in page code may be missed. Check each screen against its findings.
  • Two front ends run side by side for a time. Keep the navigation between them clear.
  • Session and role checks must match in the API, or access may widen.

This is a template, not a plan for one application. Cutover shows where each finding is in the code, and the team decides the order.
